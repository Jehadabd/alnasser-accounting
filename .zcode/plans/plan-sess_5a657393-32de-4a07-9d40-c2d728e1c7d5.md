# الخطة الشاملة: إعادة هندسة الأنظمة الأربعة

## القرارات الهندسية المعتمدة
- ✅ **كتالوج موحد مركزياً** عبر Firebase + `sync_uuid` لكل منتج.
- ✅ **سجل تعديلات كامل** (device_id + جدول `product_edit_history`).
- ✅ **خصم محلي متطابق** (كل جهاز يخصم محلياً عند البيع + عند الاستقبال).
- ✅ **خطة شاملة** لكل الأنظمة الأربعة، تُنفّذ على مراحل متتابعة.

## 🔴 المرحلة 0: الأساس البنيوي (هجرات قاعدة البيانات + النماذج)

قبل أي منطق، نضيف البنية التحتية:

### 0.1 جدول المنتجات (`products`)
أعمدة جديدة:
- `sync_uuid TEXT` — معرّف المزامنة الفريد للمنتج (مثل العملاء).
- `created_by_device_id TEXT` — الجهاز الذي أنشأ المنتج.
- `last_modified_by_device_id TEXT` — آخر جهاز عدّل.
- `last_synced_at TEXT` — آخر مزامنة للمنتج.
- فهرس فريد على `sync_uuid WHERE sync_uuid IS NOT NULL`.

### 0.2 جدول جديد: `product_edit_history`
سجل كامل لكل تعديل (السعر، الكمية، الاسم، إلخ):
```
- id, product_id (FK), product_sync_uuid
- field_changed (price/stock/name/cost/...)
- old_value, new_value (JSON)
- edit_type (manual_edit / sale / purchase / sync_in / stock_adjust)
- device_id (من عدّل)
- user_id, username
- created_at
- invoice_uuid (لو التعديل ناتج عن فاتورة)
```

### 0.3 جدول `invoice_items`
- `product_sync_uuid TEXT` — رابط ذري للمنتج بدل `product_id` المحلي.

### 0.4 تحديث النماذج
- `Product`: حقول `syncUuid`, `createdByDeviceId`, `lastModifiedByDeviceId`.
- `InvoiceItem`: حقل `productSyncUuid`.

### 0.5 هجرة بيانات للمنتجات الموجودة
- توليد `sync_uuid` لكل منتج محلي بلا UUID.
- تعيين `created_by_device_id` = رقم هذا الجهاز.

## 🟠 المرحلة 1: خدمة مزامنة المنتجات (`ProductSyncService`)

ملف جديد `lib/services/firebase_sync/product_sync_service.dart`:

### 1.1 الرفع
- `syncPendingProducts()`: يرفع المنتجات بـ `last_synced_at IS NULL` إلى `collection('products')`.
- `uploadProductNow(syncUuid)`: رفع فوري لمنتج واحد بعد إنشائه/تعديله.
- الـ payload يحوي: بيانات المنتج + `device_id` + `lastModifiedAt` + `sync_uuid`.

### 1.2 الاستقبال (`_processIncomingProduct`)
- مستمع على `collection('products')`.
- مطابقة بـ `sync_uuid` (INSERT جديد لو غير موجود، UPDATE لو موجود بأحدث `last_modified_at`).
- إدمبوتنت بفحص `last_modified_at`.
- **عدم خصم المخزون هنا** (المخزون يُخصم عبر الفواتير فقط).

### 1.3 التكامل مع شاشات المنتجات
- بعد `insertProduct` / `updateProduct`: استدعاء `uploadProductNow`.
- بعد `adjustProductStock` (التعديل اليدوي): تسجيل في `product_edit_history` + رفع.

### 1.4 الربط في `invoice_items`
- عند حفظ فاتورة: تعيين `product_sync_uuid` لكل item من المنتج.

## 🟢 المرحلة 2: خصم المخزون عند استقبال فاتورة مستوردة

### 2.1 تحديث `_processIncomingInvoice`
بعد إدراج items في `db.transaction`:
- لكل item: مطابقة المنتج عبر `product_sync_uuid` (من item المرفوع).
- استدعاء `adjustProductStock` داخل نفس الـ transaction.
- **منع الخصم المزدوج**: الفاتورة المُنشئة محلياً خُصمت عند البيع، والمستوردة تُخصم عند الاستقبال. `is_created_by_me` يحدد ذلك.

### 2.2 تحديث `_buildInvoiceBundlePayload`
- إضافة `product_sync_uuid` لكل item في الـ payload المرفوع.
- إضافة `unit_hierarchy` للمنتج (مطلوب لحساب معدل التحويل على المستقبِل).

### 2.3 تحديث `inventory_helpers.dart`
- `adjustStockForItems` يقبل `product_sync_uuid` للمطابقة بدل/مع `product_id`.

## ⚠️ تنبيهات مهمة

1. **خصم المخزون المتراكم**: عند إقلاع جهاز بعد انطفاء، سيستقبل فواتير كثيرة ويخصم المخزون لكل واحدة. يجب ضمان أن الخصم لا يتكرر (الإدمبوتنت عبر `invoice_uuid` + فحص سبق الخصم).

2. **مطابقة المنتجات الموجودة**: منتجات موجودة على أجهزة مختلفة بأسماء مطابقة ستُدمج عبر `sync_uuid` بعد الهجرة. لو اختلفت الأسعار/التكلفة بين الأجهزة، نحتاج سياسة دمج (الأحدث يفوز؟ نسأل المستخدم؟).

3. **المنتجات غير المطابقة**: فاتورة واردة بمنتج غير موجود محلياً (لم يُزامَن الكتالوج بعد) → نحتاج آلية انتظار/إنشاء مؤقت.

4. **حجم الهجرة**: مع آلاف المنتجات على عدة أجهزة، الهجرة الأولية ستكون ضخمة. نحتاج batch processing للمزامنة الأولى.

5. **التقارير التاريخية**: الفواتير القديمة (قبل التحديث) قد لا تحوي `product_sync_uuid` في items. تقاريرها ستعمل لكن بدون فلترة الجهاز على مستوى الصنف.

الخطة جاهزة للتنفيذ على مراحل. نبدأ بالمرحلة 0 (الأساس البنيوي) فور الموافقة.
