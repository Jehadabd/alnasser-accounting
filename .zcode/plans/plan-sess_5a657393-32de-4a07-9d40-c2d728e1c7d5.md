# خطة إصلاح نظام رقم الفاتورة المركّب والهجرة

## التشخيص (المشاكل المؤكدة)

1. **هجرة مكسورة** في `database_migrations.dart` (سطر 760-770): `import` داخل دالة = كود Dart غير صالح. النتيجة: الهجرة دائماً تستخدم رقم جهاز = 1.
2. **تسلسل خاطئ في الهجرة** (سطر 741-742): تستخدم `monthly_sequence_number` الموجود (الذي يكون NULL غالباً)، فتسقط لـ `seq = id` = أرقام فوضوية ضخمة.
3. **عمود خاطئ** في `database_service.dart` سطر 641: `invoice_number_label` (غير موجود) بدلاً من `invoice_number` → يعرض الـ id دائماً في كشف الحساب.
4. **بحث خاطئ** في `invoice_dao.dart` سطر 62: يبحث في `id` و`invoice_number` معاً.
5. **عشرات المواقع** تعرض `id` الداخلي بدلاً من `invoice_number` في الشاشات والخدمات.

## القرارات المعتمدة (من إجاباتك)

- ✅ ترتيب هجرة الفواتير القديمة: **حسب تاريخ الفاتورة (الأقدم أولاً)** داخل كل (سنة+شهر).
- ✅ تنسيق الرقم: **متصل بلا فواصل** (مثل `120260815`).
- ✅ المعاملات المالية: **تبقى مرتبطة بالـ id داخلياً، لكن وصفها يعرض الرقم التجاري**.
- ✅ نطاق الإصلاح: **كل المواقع** (الشاشات الأساسية + الإضافية + خدمات التصدير).
- ✅ **قيد فريد مركّب** على (creator_device_id, monthly_sequence_number) مع parts التاريخ. لا تعارض ممكن بين الأجهزة (كما أشرت).

## الخطوة 1: إصلاح الهجرة `database_migrations.dart`

**أ) إضافة `import` صحيح أعلى الملف:**
```dart
import 'package:shared_preferences/shared_preferences.dart';
```

**ب) حذف الدالتين المكسورتين** `import_shared_prefs()` و `import_dynamic()` (سطر 760-770).

**ج) إعادة كتابة `_migrateInvoiceNumbers(db)` بالكامل:**
- جلب `invoice_device_id` مباشرة من SharedPreferences (بدون كود ديناميكي مكسور).
- إضافة `import 'package:shared_preferences/shared_preferences.dart'` أعلى الملف.
- جلب الفواتير بدون `invoice_number` مرتبة حسب `invoice_date ASC` ضمن كل (سنة، شهر).
- **حساب التسلسل الشهري من الصفر**: لكل مجموعة (سنة+شهر)، نرقّم الفواتير تصاعدياً (1, 2, 3...).
- تحديث `invoice_number` و `monthly_sequence_number` معاً.
- إضافة عمودي `invoice_year` و `invoice_month` (INTEGER) لتسهيل القيد الفريد المركّب.

**د) إضافة أعمدة مساعدة + قيد فريد مركّب** في `ensureSchema`:
```sql
ALTER TABLE invoices ADD COLUMN invoice_year INTEGER;
ALTER TABLE invoices ADD COLUMN invoice_month INTEGER;
CREATE UNIQUE INDEX IF NOT EXISTS idx_invoices_unique_composite
  ON invoices(creator_device_id, invoice_year, invoice_month, monthly_sequence_number);
```

## المخاطر والتنبيهات

- ⚠️ **الهجرة ستُعيد توليد أرقام كل الفواتير القديمة** - هذا مقصود (الفواتير الحالية أرقامها خاطئة/فوضوية). لكن قد يربك المستخدم إن كان قد حفظ أرقاماً قديمة ورقياً.
- ⚠️ القيد الفريد المركّب قد يفشل إن كانت هناك فواتير مكررة حالياً (نفس الجهاز، نفس الشهر، نفس التسلسل) - الهجرة ستُصلح هذا لأنها تعيد التسلسل من الصفر.
- ℹ️ لن أمسح الـ `id` الداخلي إطلاقاً - سيبقى للتتبع التقني والربط الداخلي فقط.
